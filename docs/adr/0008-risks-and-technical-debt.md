# ADR-0008. Риски, технический долг релиза 1 и порядок реализации

**Статус:** Принято
**Дата:** 2026-10-27
**Связано:** ADR-0001–0007; backlog раздел 4 (зависимости), раздел 5 (G-01–G-30), раздел 6 (Q-10–Q-32); решения заказчика В-01–В-14; `docs/legal-questions.md`

## Контекст

R1 — рабочий пилот на Chromium и `/survey`. Дизайна, текстов ПДн, домена и хостинга пока нет, установки у клиента в R1 нет (В-07). Многие вопросы к заказчику отложены «до фичи». Здесь явно записано, на что мы сознательно идём и в каком порядке строим, чтобы открытые вопросы не блокировали работу.

## Решение

### Риски

| # | Риск | Вероятность / влияние | Мера |
| --- | --- | --- | --- |
| Р-1 | Деанонимизация комментариев (G-04). Порог считается по фактически ответившим в момент отправки (В-02), поэтому первые двое за день анонимный комментарий оставить не могут. Автор — минимум третий ответивший; при ровно трёх ответивших круг сужается до одного человека, если известен порядок ответов | Средняя / высокое (доверие, 152-ФЗ) | ADR-0005: отдельный эндпоинт, UUID v4, без логов, показ после закрытия дня, один комментарий в день. В кабинете и экспорте не показываются время и порядок ответов. Если риск подтвердится на пилоте — дополнительно проверять порог при закрытии дня (вопрос к заказчику, В-18) |
| Р-2 | Ошибки часовых поясов и границ дня (G-17) | Высокая / высокое | Один сервис времени проекта, `CarbonImmutable`, unit-тесты на UTC±, полночь, смену TZ; правила В-13 зафиксированы в ADR-0004; ленивое открытие дня при задержке Scheduler |
| Р-3 | Сбой Scheduler или воркера: день не открыт, письма не ушли | Средняя / высокое | Идемпотентное открытие по запросу, `/health` проверяет Horizon, отдельный супервизор `mail` |
| Р-4 | Эрозия границ модулей | Высокая / среднее | deptrac или arch-тест в CI (ADR-0001) |
| Р-5 | Утечка ключа шифрования раскрывает действующие коды приглашения (В-03) | Низкая / низкое | Код сам по себе доступа не даёт (нужно одобрение); ключи в env, отдельно от `APP_KEY`; массовый перевыпуск кодов при компрометации |
| Р-6 | Расширение работает только с одним доменом, заданным при сборке | Определено / низкое в R1 | On-premise вне R1 (В-07); поле «адрес сервера» с `optional_host_permissions` — после R1 |
| Р-7 | Модерация магазинов отклоняет или затягивает публикацию; аккаунтов пока нет (Q-09) | Средняя / среднее | Минимальные разрешения, описание «не читаем вкладки и историю», `/survey` как запасной канал; Яндекс Браузер ставит расширение из Chrome Web Store (В-08) |
| Р-8 | WXT 0.x — ломающие изменения | Средняя / низкое | Фиксированная версия, обновление отдельным PR |
| Р-9 | Firefox MV3: явная выдача host-разрешения; Safari: другая модель фона и подпись (R2/R3) | Определено / низкое | Правила ADR-0003: без состояния в памяти, только общие API |
| Р-10 | Лицензия Redis 8 (RSALv2/SSPL/AGPLv3) при будущей поставке клиентам | Низкая в R1 / среднее после | В R1 поставки клиентам нет; используем Redis 8 (В-10). Лицензию проверяем перед первой поставкой; продукт не меняем |
| Р-11 | Horizon работает только с Redis: замена брокера (п. 3.5.5) лишит панели | Низкая / низкое | Бизнес-код не зависит от драйвера; мониторинг очередей заменяем |
| Р-12 | Перебор 6-значных кодов | Низкая / высокое | HMAC, 5 попыток, лимиты по email и IP |
| Р-13 | Открытые вопросы Q-15–Q-21 меняют поведение после реализации | Высокая / среднее | Схема ADR-0004 от них не зависит; поведение в сервисах настраивается конфигурацией и покрыто тестами, правки локальны |
| Р-14 | Удалённые данные живут в резервных копиях 14 дней | Определено / среднее | Отразить в политике ПДн (заказчик), вопрос юристу (ЮВ-1) |
| Р-15 | Нет макетов (Q-04) — переделка интерфейса | Высокая / среднее | Нейтральная вёрстка на Tailwind; форма опроса изолирована в `packages/survey-ui` |
| Р-16 | Сессия `/survey` обрывается после 24 ч бездействия (В-09): сотрудник без расширения входит по коду почти каждый рабочий день и всегда после выходных. Это расходится с ТЗ п. 4.4 и F-005 (30 дней) | Высокая / среднее (цель отклика 70%) | Сроки задаются в env и меняются без релиза; продвигать расширение как основной канал; замерить отклик через `/survey` на пилоте |
| Р-17 | Мягкое удаление (В-05): сырой запрос или отчёт без учёта `deleted_at` покажет удалённые данные | Средняя / высокое (ПДн) | Global scope `SoftDeletes`; чтение только через репозитории; тест «удалённый аккаунт и проект не видны» на каждый эндпоинт чтения и на экспорт |
| Р-18 | Мягкое удаление и ручная физическая очистка могут не соответствовать праву субъекта на уничтожение ПДн и сроку по 152-ФЗ; ТЗ п. 9.2.4 требует удаления | Средняя / высокое (регуляторный риск) | Вопрос юристу (ЮВ-1); у команды очистки есть режим «старше N дней», дата запроса фиксируется; при отрицательном заключении — включить автоматическую очистку в Scheduler (изменение конфигурации, не схемы) |
| Р-19 | Повторная регистрация на email мягко удалённого аккаунта создаёт новый аккаунт; восстановление старого вручную может дать два аккаунта на один email | Низкая / низкое | Частичный уникальный индекс по email; восстановление — только командой системного администратора с проверкой конфликта |
| Р-20 | Запись словаря псевдонимов удаляется физически, а аккаунт — мягко (В-04 + В-05): после восстановления аккаунта старые сводки не покажут имя | Низкая / низкое | Сознательная асимметрия (ADR-0005); описать в руководстве администратора |
| Р-21 | Хранение `user_consents` после удаления аккаунта (В-11) может быть признано избыточным или, наоборот, недостаточным доказательством | Средняя / среднее | Вопрос юристу (ЮВ-2); таблица без ПДн, решение меняется без миграции схемы |

### Сознательный технический долг R1

| Долг | Почему приемлемо | Когда вернуть |
| --- | --- | --- |
| Кабинет на Inertia без REST (`/api/v1` — только для каналов ответа), решение В-01 | Вдвое меньше работы; сервисы канал-независимы | При мобильном приложении кабинета |
| Изоляция проектов только на уровне приложения, без RLS | Policy + scope + тест на каждый эндпоинт | При многоарендной продаже или аудите безопасности |
| Физическая очистка мягко удалённых данных — вручную (В-05) | Решение заказчика, позволяет восстанавливать удалённое | После заключения юриста: возможно, автоматическая очистка по сроку |
| Polling вместо WebSocket | Задачи редкие; нет нового процесса | Если появятся realtime-алерты |
| Флаги функций — своя таблица без UI | Один флаг `alerts` | С тарифами |
| Рабочий календарь только по дням недели | F-027 отложен | С F-027 |
| Внешние метрики — только контракт `MetricSource` | Трекеры не в пилоте | С интеграциями |
| Типы API на клиенте пишутся вручную | API небольшой | При расхождениях — генерация из OpenAPI |
| Экспорты на локальном диске | Один сервер | При нескольких узлах — S3-совместимое хранилище |
| Нет e2e-тестов расширения | Ручной чек-лист перед публикацией | После стабилизации экранов |
| Расширение с одним доменом из сборки | On-premise вне R1 (В-07) | Перед первой установкой у клиента |
| Тексты согласия, промпта, en-вопросов — заглушки | Q-08 | По мере поставки текстов |
| Нет prod-compose, бэкапов, мониторинга | Q-07 | При выборе хостинга |

### Порядок реализации R1

Шаги следуют зависимостям backlog (раздел 4.2). Каждый шаг — законченный PR с тестами и обновлённым OpenAPI; новые типы сущностей описываются в `docs/new_types.md` (В-12).

1. **Фундамент.** Монорепо, `compose.yaml` (Redis 8), Laravel, каркас модулей и Shared (формат ошибок, `Accept-Language`, `Channel`), Horizon с очередями, Scheduler, CI (Pint, Larastan 6, тесты, audit), `/health`. (F-064, F-065, F-067, F-069, F-070, F-071)
2. **Identity + Notifications.** Вход по коду (HMAC, лимиты); письма в очереди `mail`; сессии (24 ч бездействия / 14 дней, middleware абсолютного срока) и токены устройств; общая страница профиля; согласие с версиями и `consent_required`; устройства. (F-001–F-005, F-068)
3. **Projects.** Проект (с открытием дня при создании); membership и роли с Policies и тестами матрицы; код приглашения (HMAC + шифрованная копия); заявки и модерация; флаг участия; передача владения; исключение; мягкое удаление проекта с кодом из письма; флаги и тариф; слушатели Audit. (F-007–F-011, F-013–F-018, F-059, F-061, F-077)
4. **Survey.** Банк вопросов (сидер), вопросы проекта, версии, состав и ротация, предпросмотр, «опрос дня» с открытием и закрытием по TZ, набор по умолчанию. (F-019–F-026, F-028, F-029)
5. **Responses + общий пакет формы.** API опроса; отправка и изменение ответа; анонимные комментарии по ADR-0005 (порог по ответившим, один в день, показ после закрытия); `packages/survey-ui`; страница `/survey`. (F-031–F-033, F-037, F-038, F-062)
6. **Расширение Chromium.** Каркас WXT, экраны (включая экран согласия), бейдж, черновики, сборки Chrome и Edge, материалы для Chrome Web Store и Edge Add-ons. (F-034–F-036, F-039)
7. **Analytics.** Агрегаты по событиям и ночью (без мягко удалённых ответов); индекс (unit-тесты); участие по снимку ожидаемых; дашборд, тепловая карта, графики, лента, карточка участника; CSV-экспорт. (F-040–F-049, F-051)
8. **Права субъекта и завершение.** Выгрузка и мягкое удаление аккаунта через `PersonalDataLifecycle`; команды ручной очистки `privacy:purge-*`; сидер демо-данных; замеры производительности; README, ER, руководство администратора (включая регламент ручной очистки). (F-006, F-072, F-073, F-074)

Задел E-09 (`external_identities`, `integration_connections`, `Channel::Telegram`) создаётся в шагах 2–5 попутно, без логики.

## Рассмотренные альтернативы

1. **Ждать ответов на все вопросы до начала разработки.** Надолго блокирует R1. Отклонено: схема спроектирована так, чтобы ответы меняли сервисы, а не таблицы.
2. **Сразу закрыть долг (REST для кабинета, RLS, WebSocket, автоматическая очистка).** Удлиняет R1 без пользы для пилота; автоматическую очистку заказчик не выбрал (В-05). Отклонено.

## Последствия

- Долг из таблицы выше пересматривается при планировании R2.
- Заключение юриста (`docs/legal-questions.md`) может изменить В-05 и В-11. Схема рассчитана на это: изменения будут в сервисах и Scheduler, не в таблицах.
- Новые решения заказчика оформляются новым ADR, который заменяет прежний.
