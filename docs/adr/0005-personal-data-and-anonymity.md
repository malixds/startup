# ADR-0005. Персональные данные, анонимность и права субъекта

**Статус:** Принято
**Дата:** 2026-10-27
**Связано:** ТЗ п. 4.1.5, 4.8, 6.5, 8.2–8.4, 9.1.7, 9.2, 9.3.1; CLAUDE.md «Персональные данные и безопасность», «AI-сводка»; backlog F-003, F-006, F-033, F-059, F-062, G-04, G-05, G-06, G-11, G-12, G-13, G-28, Q-10, Q-11, Q-15, Q-21, Q-22, Q-31; решения заказчика В-02, В-04, В-05, В-06, В-11, В-14; вопросы юристу — `docs/legal-questions.md`

## Контекст

Система обрабатывает ПДн и самооценку состояния сотрудников (152-ФЗ, серверы в РФ). ТЗ обещает анонимные комментарии, но backlog фиксирует два противоречия:

- **G-04.** У анонимного комментария нет `user_id` и времени, однако связь с автором можно восстановить: (а) если комментарий уходит одним запросом с подписанным ответом — по порядку вставки, последовательным ID и `updated_at` ответа; (б) по access-логу веб-сервера (хранится до 30 дней), где есть IP, время и путь.
- **G-11.** Неясно, в каком виде хранится AI-сводка; при удалении аккаунта имена остаются в сводках и журнале; нет правил для данных удалённого проекта.

Решения заказчика: анонимные комментарии показываются после закрытия дня, один комментарий на участника в день, порог «< 3» — по фактически ответившим (В-02); сводки хранятся с псевдонимами (В-04); удаление проекта и аккаунта мягкое (В-05); минимальная запись о согласии остаётся после удаления (В-11). Пункты В-05 и В-11 переданы юристу.

## Решение

### 1. Где лежат ПДн (реестр)

| Данные | Где | Срок |
| --- | --- | --- |
| Email, имя, язык | `users` | До удаления аккаунта (мягкое, затем ручная очистка) |
| Email до регистрации, коды | `login_codes` (код — HMAC) | Просроченные чистятся ежечасно |
| Устройства (название, последнее использование) | `personal_access_tokens` (токен — SHA-256) | До отзыва; при удалении аккаунта удаляются сразу |
| Сессии | Redis (драйвер `redis` не хранит IP и user-agent) | 24 ч бездействия / 14 дней; при удалении аккаунта удаляются сразу |
| Факт согласия | `user_consents`: дата, версия, ID, без ПДн | Остаётся после удаления аккаунта (В-11, вопрос юристу) |
| Членство, роли, заявки | `memberships`, `join_requests` | До очистки аккаунта или проекта |
| Ответы и подписанные комментарии | `responses`, `response_answers` | Мягко удаляются при удалении аккаунта и исключении с удалением; физически — при ручной очистке |
| Анонимные комментарии | `anonymous_comments` (связи с автором нет, но в тексте могут быть сведения о людях) | До очистки проекта |
| Агрегаты по участнику | `daily_member_stats` (`membership_id`) | Пересчитываются без мягко удалённых ответов |
| Журнал действий | `audit_log` (только идентификаторы) | 1 год, при мягком удалении не меняется |
| Файлы экспорта | `storage/app/exports` | 24 часа |
| Словарь псевдонимов (R2) | `ai_summary_pseudonyms` | Запись удаляется физически при удалении участника (В-04) |
| Логи Nginx | файлы в томе | ≤ 30 дней (ротация) |
| Логи приложения | stderr / файл | Без тел запросов и IP (см. п. 3) |
| Резервные копии | при выборе хостинга | 14 дней |

Каждый модуль, хранящий строки о пользователе или проекте, реализует `PersonalDataLifecycle` (`export`, `onAccountDeleted`/`onProjectDeleted`, `purgeUser`/`purgeProject`, ADR-0001).

### 2. Согласие на ПДн (В-06, В-11 — решено)

- Тексты хранятся в БД (`consent_documents`: версия + ru/en). Системный администратор публикует их artisan-командой из файла, без релиза; UI в R1 не нужен. Пока используется текст-заглушка (Q-08).
- Согласие принимается на отдельном экране отдельной галочкой; создаётся запись `user_consents(user_id, consent_document_id, accepted_at)` без IP.
- Пока текущая версия не принята, API отвечает `consent_required`, а **приём ответов и анонимных комментариев отклоняется** (ADR-0003). Расширение и `/survey` показывают экран согласия при следующем открытии. Так новую версию получает и пользователь с бессрочным токеном (G-12).
- После удаления аккаунта (в том числе после ручной физической очистки) остаётся только запись «ID пользователя, версия текста, дата». Email, имя и IP в ней нет. Сам ID после очистки `users` ни на кого не указывает. **Вопрос юристу:** достаточно ли такой записи, чтобы подтвердить согласие, и законно ли её хранить (`docs/legal-questions.md`, ЮВ-2).

### 3. Анонимность комментариев (G-04, G-05, G-06; В-02 — решено)

Меры R1:
1. **Отдельный эндпоинт** `POST .../anonymous-comments`, отдельный запрос клиента, отдельная транзакция. Текст не попадает в общий `PUT response`.
2. **Таблица без связей:** `id uuid v4` (случайный), `project_id`, `local_date`, `body`. Нет `created_at`/`updated_at`, нет `user_id`, нет внешнего ключа на ответ.
3. **Логи:**
   - в Nginx для этого location `access_log off`;
   - в Laravel маршрут исключён из логирования тел и отчётов об ошибках (никаких `request()->all()` в контексте исключений), Telescope не устанавливается;
   - в PostgreSQL `log_statement = none`, `log_min_duration_statement` в продакшене выключен;
   - драйвер мониторинга обязан вырезать тела запросов (ADR-0002).
4. **Нельзя изменить или удалить** (п. 6.5.4).
5. **Один анонимный комментарий на участника в день** (G-05). Счётчик хранится в Redis с ключом «пользователь + проект + день» и TTL до конца дня. Он знает только факт отправки, а не текст и не ID комментария. AOF включён, чтобы перезапуск Redis не сбросил лимит.
6. **Показ после закрытия дня (вариант B).** Комментарий записывается сразу, но кабинет, лента, счётчик «новых комментариев» и экспорт показывают анонимные комментарии только за закрытые дни. Поэтому администратор не может сопоставить появление комментария с появлением ответа конкретного человека.
7. **Порог «< 3» — по фактически ответившим за день (G-06).** Responses считает неудалённые ответы текущего дня **в момент отправки**, включая ответ автора. Анонимный комментарий доступен, если у автора уже есть ответ за день и ответивших не меньше трёх. Иначе галочка недоступна, рядом показывается причина «пока ответили меньше 3 человек» и подсказка: добавить анонимный комментарий можно позже через «Изменить ответ». Сам порог задаётся в конфигурации.

Что даёт порог по фактически ответившим, и что остаётся:
- Автор всегда находится среди ответивших за этот день, которых администратор видит поимённо, и их не меньше трёх в момент отправки. Это k-анонимность с k ≥ 3 внутри дня. Порог по ожидаемым участникам такого не гарантировал: можно было отправить анонимный комментарий, когда ответил один человек.
- **Остаточный риск 1 — порядок ответов.** Первые двое ответивших за день анонимный комментарий оставить не могут. Значит, автор — третий или более поздний ответивший, а при показе после закрытия дня администратор видит, кто ответил в числе первых. В худшем случае (ровно 3 ответивших, комментарий есть) круг подозреваемых сужается до одного человека: третьего по времени. Мера в R1: в кабинете не показывать порядок и точное время ответов за день — только дату; время отправки (`submitted_at`) в экспорт и интерфейс не выводится. Полностью риск снимается, только если перенести решение о публикации на закрытие дня (например, при < 3 ответивших к закрытию комментарий не публикуется). Это зафиксировано в ADR-0008 (Р-1) как предмет будущего решения.
- **Остаточный риск 2 — сотрудник видит число ответивших.** Ответ «анонимность недоступна, пока ответили меньше 3» сообщает сотруднику, что сегодня ответили не больше двух коллег. Утечка небольшая, принимаем.
- **Остаточный риск 3 — администратор БД** видит физический порядок строк. Принимаем, он вне модели угроз «администратор проекта».
- Мягкое удаление ответа (исключение участника, удаление аккаунта) может задним числом снизить число ответивших за прошлые дни ниже трёх. Опубликованные комментарии это не скрывает: порог проверяется только в момент отправки.

### 4. Удаление и G-11 (В-04, В-05 — решено, В-05 — вопрос юристу)

Принципы:
- **Хранить идентификаторы, имена подставлять при показе.** Тогда скрытие или удаление строки участника убирает его имя отовсюду.
- **Удаление аккаунта и проекта — мягкое** (`deleted_at`, ADR-0004). Физически данные удаляет системный администратор вручную командой очистки.

| Ситуация | Ответы, подписанные комментарии, агрегаты | Анонимные комментарии | Журнал действий | AI-сводки (R2) | Учётные данные, экспорты |
| --- | --- | --- | --- | --- | --- |
| Удаление аккаунта (п. 9.2.4) | `responses.deleted_at` во всех проектах, агрегаты пересчитываются | Остаются | Без изменений, автор показывается как «Удалённый пользователь» | Запись словаря удаляется, в тексте остаётся «Участник N» | Токены, сессии, коды удаляются сразу; свежие файлы экспорта проектов пользователя удаляются |
| Исключение «оставить» (п. 4.8) | Остаются, показываются как «Бывший участник» | Остаются | Без изменений | Без изменений (имя заменяется на «Бывший участник») | — |
| Исключение «удалить» | `responses.deleted_at` (временно, В-15), агрегаты пересчитываются | Остаются | Без изменений | Запись словаря удаляется | Как выше |
| Удаление проекта | `projects.deleted_at`: всё внутри недоступно | Скрыты вместе с проектом | Хранятся 1 год | Скрыты вместе с проектом | Файлы экспорта удаляются; код приглашения отзывается |
| Ручная очистка (`privacy:purge-*`) | Физическое удаление | При очистке проекта — удаляются | Остаются до истечения года (ЮВ-1) | Удаляются | — |

**Как это сочетается с правом субъекта на удаление (G-11).** Для пользователя аккаунт и подписанные ответы исчезают сразу: ни администратор проекта, ни аналитика, ни экспорт их больше не видят. Хранение в БД при этом продолжается до ручной очистки. Это расходится с буквой ТЗ п. 9.2.4 («удаляются аккаунт и подписанные ответы») и, возможно, с требованиями 152-ФЗ к уничтожению ПДн по запросу субъекта в установленный срок. Временное решение по В-05: мягкое удаление плюс ручная очистка. Пока юрист не ответит:
- у команды очистки есть режим «все мягко удалённые старше N дней», чтобы при необходимости выполнять её регулярно;
- в журнале системного администратора фиксируется дата запроса на удаление, чтобы можно было отсчитать срок.

Вопросы юристу — ЮВ-1 в `docs/legal-questions.md`.

**AI-сводки (R2, В-04).** Хранится **текст с псевдонимами** и словарь `псевдоним → membership_id` без имён. Обратная подстановка имён (п. 8.3.2) делается только при показе. При удалении аккаунта или исключении с удалением ответов запись словаря удаляется **физически**: сводку уже нельзя связать с человеком, даже если аккаунт потом восстановят из мягкого удаления. Это сознательная асимметрия.

### 5. Выгрузка «мои данные» и профиль (В-14 — решено)

- Общая страница профиля (Inertia) доступна любому аккаунту, включая сотрудника без ролей в кабинете. Там: устройства, выгрузка, удаление аккаунта. Ссылки на неё есть в `/survey` и в настройках расширения.
- Выгрузка — JSON-архив, собираемый из всех `PersonalDataLifecycle::export` в очереди `default`; ссылка живёт 24 часа. Анонимные комментарии в выгрузку не входят, потому что система не знает автора. Формат и состав уточняются в Q-31.
- Удаление аккаунта владельцем проекта — Q-22 (по умолчанию нельзя, пока не передано владение, п. 2.3.2).

### 6. Прочее

- IP с ответами не хранится нигде. Для rate limiting IP используется только в памяти: ключ в Redis с коротким TTL.
- В текстах интерфейса, писем, категорий, материалов для магазинов и промптов нет медицинских терминов (G-20).
- Администратор одного проекта не видит данные другого: проектный scope в репозиториях + Policy + feature-тест на каждый эндпоинт.

## Рассмотренные альтернативы

1. **Анонимный комментарий в общей таблице ответов с флагом `is_anonymous` и `user_id = null`.** Связь по ID ответа и времени сохраняется. Отклонено (противоречит п. 6.5.3).
2. **Показ анонимных комментариев сразу (вариант A) или буферизация в Redis с пакетной записью (вариант C).** Отклонено заказчиком в пользу B (В-02).
3. **Порог по ожидаемым участникам.** Отклонено заказчиком (В-02).
4. **Снимок имён в сводках и журнале.** Нарушает право на удаление. Отклонено.
5. **Немедленное физическое удаление аккаунта и проекта.** Изначальная рекомендация. Заказчик выбрал мягкое удаление (В-05), вопрос передан юристу.

## Последствия

- (+) Администратор проекта не видит удалённые данные и не может связать анонимный комментарий с автором точнее, чем «один из ≥ 3 ответивших».
- (+) Случайно удалённый проект можно восстановить.
- (−) **Юридический риск:** мягко удалённые ПДн хранятся до ручной очистки; удалённые данные остаются и в резервных копиях до 14 дней. Нужно заключение юриста и отражение в политике обработки ПДн (ADR-0008, Р-14, Р-18).
- (−) Ручная очистка — операционная обязанность системного администратора заказчика. Если её не выполнять, данные копятся бессрочно.
- (−) Первые двое ответивших за день не могут оставить анонимный комментарий; остаточный риск сужения круга при ровно трёх ответивших (Р-1).
- (−) Руководитель видит анонимные комментарии на следующий день.
