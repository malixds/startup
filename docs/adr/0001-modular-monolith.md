# ADR-0001. Модульный монолит: границы модулей и взаимодействие

**Статус:** Принято
**Дата:** 2026-10-27
**Связано:** ТЗ п. 3, 3.2, 3.3, 3.6, 10; CLAUDE.md «Архитектурные правила» 1–3, 5, 7, 8; backlog F-031, F-066, F-075–F-077; решения заказчика В-01, В-05, В-07, В-12, В-15, В-17, В-19

## Контекст

- Команда маленькая, проект на стадии MVP, выпуск по релизам R1 → R2 → R3 (Q-03). Нагрузка пилота ничтожная.
- ТЗ и CLAUDE.md уже фиксируют модульный монолит на Laravel и запрещают модулю обращаться к таблицам другого модуля.
- Telegram-бот, трекеры, алерты и биллинг должны добавляться без переделки модулей Survey, Responses и Analytics (п. 3.3.3, раздел 10).
- On-premise в R1 не входит (В-07). Принцип «вся конфигурация через env» сохраняется.

## Решение

**Одно Laravel-приложение: один деплой, одна БД.** Код разделён на модули в `backend/app/Modules/<Module>/` (namespace `App\Modules\<Module>`), сторонние пакеты модульности не используются.

### Модули и владение данными

| Модуль | Отвечает за | Владеет таблицами (см. ADR-0004) |
| --- | --- | --- |
| Identity | Аккаунты, вход по коду, токены устройств, сессии, согласие на ПДн, внешние идентичности, профиль, оркестрация прав субъекта ПДн | `users`, `login_codes`, `personal_access_tokens`, `consent_documents`, `user_consents`, `external_identities` |
| Projects | Проекты, участие и роли, коды приглашения, заявки, флаги функций и тариф, рабочий календарь; оркестрация удаления проекта и исключения участника | `projects`, `memberships`, `invite_codes`, `join_requests`, `project_features` |
| Survey | Банк и вопросы проекта, версии, состав опроса и ротация, «опрос дня», открытие и закрытие дня | `questions`, `question_versions`, `survey_configs`, `survey_config_items`, `survey_days`, `survey_day_questions` |
| Responses | Канал-независимый приём ответов и комментариев (всегда привязаны к участнику) | `responses`, `response_answers` |
| Analytics | Дневные агрегаты, индекс, участие, данные дашборда, экспорт CSV (PDF — R2) | `daily_member_stats`, `daily_project_stats`, `daily_question_stats`, `exports` |
| AI | R2. В R1 — пустой модуль с контрактом `LlmProvider` и событием `SummaryGenerated` | (R2) `ai_summaries`, `ai_summary_pseudonyms` |
| Notifications | Письма (коды, заявки), очередь `mail`, язык получателя | нет |
| Audit | Журнал действий, срок хранения 1 год | `audit_log` |
| Integrations | Пустой задел: контракт коннектора, таблица подключений | `integration_connections` |
| Shared (ядро) | `Channel`, `LocalDate`, единый формат ошибок, локализация API, базовые DTO | нет |

### Структура модуля

Структура следует правилу 8 CLAUDE.md: `Http/Controllers`, `Http/Requests`, `Contracts`, `Services`, `Repositories` (с интерфейсами), `DTO`, `Models`, `Events`, `Listeners`, `Jobs`, `Policies`, `Database/Migrations`, `Providers/<Module>ServiceProvider`, `routes`. Наружу модуль отдаёт только `Contracts`, `DTO`, `Events` и enum-ы. Модели Eloquent за пределы модуля не выходят.

### Как модули общаются

1. **Синхронно — через контракты.** Модуль A зависит от интерфейса `B\Contracts\XxxService` и получает DTO.
2. **Асинхронно — через доменные события** из п. 3.6: `MemberJoined`, `SurveyDayOpened`, `ResponseSubmitted`, `SurveyDayClosed`, `SummaryGenerated`. Имена событий не меняются. Полезная нагрузка — только идентификаторы и скаляры. Подписчики — queued listeners, каждый в своей очереди по назначению. Новые события добавляются по мере надобности.
3. **Реестр удаления и выгрузки ПДн.** Каждый модуль, хранящий данные о пользователе, участнике или проекте, реализует `PersonalDataLifecycle`. Все удаления **физические и выполняются сразу** (В-05):
   - `export(userId)` — выгрузка «мои данные»;
   - `eraseUser(userId)` — удаление аккаунта. Audit удаляет все записи журнала, где пользователь — автор или объект (В-19);
   - `eraseProject(projectId)` — удаление проекта. Audit удаляет все записи журнала этого проекта (В-19);
   - `onMemberRemoved(membershipId, deleteResponses)` — исключение участника. Responses удаляет его ответы, если выбрано «удалить» (В-15). AI (R2) всегда удаляет запись словаря псевдонимов (В-17).

   Identity и Projects вызывают все зарегистрированные реализации в одной транзакции. В R2 модуль AI добавит свою реализацию без правок остальных модулей.
4. **Внешние ключи между модулями допустимы** (`ON DELETE RESTRICT`), но каскадное удаление через границу модуля запрещено: удаление идёт через реестр. Запросы к чужим таблицам запрещены. Исключение — `user_consents.user_id` без внешнего ключа (В-11, ЮВ-2).
5. **Контроль границ в CI**: `deptrac` (dev-зависимость) или architecture-тест на PHPUnit.

### Каналы ответа (правила 2–3)

- Логика опроса находится в `Responses\Services\SurveyResponseService` и `Survey\Services\SurveyDayService`. Канал (`Channel`) передаётся параметром, HTTP эти сервисы не знают.
- Канал определяет HTTP-слой по способу аутентификации и типу клиента токена: сессия → `web`, токен `extension` → `extension`. Будущий Telegram-адаптер вызовет тот же сервис с `Channel::Telegram`.
- Ответ API опроса содержит полное описание вопросов.

### Кабинет и API (В-01)

- Каналы ответа ходят только в `/api/v1/...` (Sanctum), описанный в OpenAPI.
- Кабинет и общая страница профиля сделаны на Inertia и вызывают те же сервисы. REST для кабинета не делаем (В-01, В-14).

### Точки расширения

| Этап | Точка расширения |
| --- | --- |
| Telegram-бот | `Channel::Telegram`, `external_identities`, канал-независимые сервисы |
| Трекеры | Integrations: `integration_connections` + `TrackerConnector`; Analytics: `MetricSource` |
| Алерты | Доменные события + флаг `alerts` |
| Тарифы | `projects.plan = 'pilot'`, лимиты через `PlanLimits` |
| Мобильные приложения | Токены устройств с типом клиента `mobile` |
| On-premise (после R1) | Конфигурация через env, один compose, поле «адрес сервера» в расширении |

## Рассмотренные альтернативы

1. **Классический монолит без модулей.** Отклонён: ТЗ требует модули.
2. **Микросервисы.** Отклонены: при нагрузке пилота не нужны.
3. **`nwidart/laravel-modules`.** Отклонён как лишняя зависимость.
4. **Кабинет через `/api/v1`.** Отклонён заказчиком (В-01).

## Последствия

- (+) Один деплой, транзакции внутри процесса.
- (+) Новые каналы и функции R2 добавляются адаптерами и реализациями контрактов.
- (+) Удаление ПДн реализовано в одной точке расширения на модуль.
- (−) Границы модулей держатся на дисциплине и проверке в CI.
- (−) Физическое удаление необратимо (ADR-0008, Р-17).
- Новые типы сущностей описываются в `docs/new_types.md` (В-12).
