# ADR-0001. Модульный монолит: границы модулей и взаимодействие

**Статус:** Принято
**Дата:** 2026-10-27
**Связано:** ТЗ п. 3, 3.2, 3.3, 3.6, 9.1.7, 10; CLAUDE.md «Архитектурные правила» 1–3, 5, 7, 8; backlog F-031, F-059, F-066, F-075–F-077; решения заказчика В-01, В-05, В-07, В-12, В-15, В-17, В-19, В-21, В-23, событие `MemberParticipationChanged`

## Контекст

- Команда маленькая, стадия MVP, релизы R1 → R2 → R3 (Q-03). Нагрузка пилота ничтожная.
- ТЗ и CLAUDE.md уже требуют модульный монолит на Laravel и запрещают модулю обращаться к таблицам другого модуля.
- Telegram-бот, трекеры, алерты и биллинг должны добавляться без переделки модулей Survey, Responses и Analytics (п. 3.3.3, раздел 10).
- On-premise не входит в R1 (В-07). Принцип «вся конфигурация через env» сохраняется.

## Решение

**Одно Laravel-приложение: один деплой и одна БД.** Код разделён на модули в `backend/app/Modules/<Module>/` (namespace `App\Modules\<Module>`), сторонних пакетов модульности нет.

### Модули и владение данными

| Модуль | Отвечает за | Владеет таблицами (см. ADR-0004) |
| --- | --- | --- |
| Identity | Аккаунты, вход по коду, токены устройств, сессии, согласие ПДн, внешние идентичности, профиль, оркестрация прав субъекта ПДн | `users`, `login_codes`, `personal_access_tokens`, `consent_documents`, `user_consents`, `external_identities` |
| Projects | Проекты, участие и роли, флаг участия, коды приглашения, заявки, флаги функций и тариф, рабочий календарь; оркестрация удаления проекта и исключения участника | `projects`, `memberships`, `invite_codes`, `join_requests`, `project_features` |
| Survey | Банк и вопросы проекта, версии, состав и ротация, «опрос дня», открытие и закрытие дня | `questions`, `question_versions`, `survey_configs`, `survey_config_items`, `survey_days`, `survey_day_questions` |
| Responses | Канал-независимый приём ответов и комментариев (всегда привязаны к участнику) | `responses`, `response_answers` |
| Analytics | Дневные агрегаты, индекс, участие, дашборд, экспорт CSV (PDF — в R2) | `daily_member_stats`, `daily_project_stats`, `daily_question_stats`, `exports` |
| AI | R2. В R1 — пустой модуль с контрактом `LlmProvider` и событием `SummaryGenerated` | (R2) `ai_summaries`, `ai_summary_pseudonyms` |
| Notifications | Письма (коды, заявки), очередь `mail`, язык получателя | нет |
| Audit | Журнал действий (1 год) и реестр удалений (1 год, только для системного администратора, В-21, В-23) | `audit_log`, `deletion_log` |
| Integrations | Пустой задел: контракт коннектора, таблица подключений | `integration_connections` |
| Shared (ядро) | `Channel`, `LocalDate`, единый формат ошибок, локализация API, базовые DTO | нет |

### Структура модуля

Структура следует правилу 8 CLAUDE.md: `Http/Controllers`, `Http/Requests`, `Contracts`, `Services`, `Repositories` (с интерфейсами), `DTO`, `Models`, `Events`, `Listeners`, `Jobs`, `Policies`, `Database/Migrations`, `Providers/<Module>ServiceProvider`, `routes`. Наружу модуль отдаёт только `Contracts`, `DTO`, `Events` и enum-ы.

### Как модули общаются

1. **Синхронно — через контракты** и DTO.
2. **Асинхронно — через шесть утверждённых доменных событий:**

   | Событие | Публикует | Подписчики в R1 |
   | --- | --- | --- |
   | `MemberJoined` | Projects | Audit |
   | `MemberParticipationChanged` | Projects | Analytics (корректировка снимка ожидаемых, ADR-0004), Audit |
   | `SurveyDayOpened` | Survey | Analytics (снимок ожидаемых) |
   | `ResponseSubmitted` | Responses | Analytics (пересчёт дня) |
   | `SurveyDayClosed` | Survey | Analytics |
   | `SummaryGenerated` | AI (R2) | Audit (R2) |

   Имена событий не меняются без согласования, новые доменные события тоже добавляются только по согласованию. В событиях передаются только идентификаторы и скаляры. Подписчики — queued listeners в своём модуле. Внутренние синхронные операции (например, `onMemberRemoved`) событиями не являются и идут через контракты.
3. **Реестр удаления и выгрузки ПДн.** Каждый модуль, хранящий данные о пользователе, участнике или проекте, реализует `PersonalDataLifecycle`. Все удаления физические и выполняются сразу (В-05). Методы:
   - `export(userId)`;
   - `eraseUser(userId)` — Audit удаляет записи `audit_log`, где пользователь — автор или объект (В-19);
   - `eraseProject(projectId)` — Audit удаляет записи `audit_log` проекта (В-19);
   - `onMemberRemoved(membershipId, deleteResponses)` — Responses удаляет ответы, если выбрано «удалить» (В-15); Analytics снимает `expected` за сегодня; AI в R2 всегда удаляет запись словаря (В-17).

   В той же транзакции оркестратор вызывает `Audit\Contracts\DeletionLog::record(action, projectId, initiatorUserId)` — запись в реестр удалений (В-21). Реестр не входит в `PersonalDataLifecycle`: его записи живут 1 год независимо от удаления субъекта. Читать реестр можно только через artisan-команду системного администратора (В-23).
4. **Внешние ключи между модулями допустимы** (`ON DELETE RESTRICT`), каскадное удаление через границу модуля запрещено. Без внешних ключей, и это сделано намеренно, остаются `user_consents.user_id` (В-11) и `deletion_log.project_id` / `deletion_log.initiator_user_id` (В-21).
5. **Контроль границ в CI** — architecture-тест на PHPUnit, без новой зависимости (В-24).

### Каналы ответа (правила 2–3)

- Логика опроса лежит в `Responses\Services\SurveyResponseService` и `Survey\Services\SurveyDayService`, канал (`Channel`) передаётся параметром.
- Канал определяет HTTP-слой по способу аутентификации: сессия → `web`, токен `extension` → `extension`. Будущий Telegram-адаптер вызовет тот же сервис с `Channel::Telegram`.
- Ответ API опроса содержит полное описание вопросов.

### Кабинет и API (В-01)

- Каналы ответа работают только через `/api/v1/...` (Sanctum, OpenAPI).
- Кабинет и общая страница профиля сделаны на Inertia (В-01, В-14).

### Точки расширения

| Этап | Точка расширения |
| --- | --- |
| Telegram-бот | `Channel::Telegram`, `external_identities`, канал-независимые сервисы |
| Трекеры | Integrations: `integration_connections` + `TrackerConnector`; Analytics: `MetricSource` |
| Алерты | Шесть доменных событий + флаг `alerts` |
| Тарифы | `projects.plan = 'pilot'`, лимиты через `PlanLimits` |
| Мобильные приложения | Токены устройств с типом клиента `mobile` |
| On-premise (после R1) | Конфигурация через env, один compose, поле «адрес сервера» |

## Рассмотренные альтернативы

1. **Классический монолит без модулей.** Отклонено: ТЗ требует модули.
2. **Микросервисы.** Отклонено: для пилота это лишняя сложность.
3. **`nwidart/laravel-modules`.** Отклонено как лишняя зависимость.
4. **Кабинет через `/api/v1`.** Отклонено заказчиком (В-01).

## Последствия

- (+) Один деплой, транзакции внутри процесса.
- (+) Новые каналы и функции R2 добавляются адаптерами и реализациями контрактов.
- (+) Удаление ПДн — одна точка расширения на модуль, факт удаления фиксируется в одном реестре.
- (−) Границы модулей держатся на дисциплине и проверке в CI.
- (−) Физическое удаление необратимо (ADR-0008, Р-17).
- Новые типы сущностей описываются в `docs/new_types.md` (В-12), мелкие решения — в `docs/decisions.md`.
