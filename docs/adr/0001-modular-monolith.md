# ADR-0001. Модульный монолит: границы модулей и взаимодействие

**Статус:** Принято
**Дата:** 2026-10-27
**Связано:** ТЗ п. 3, 3.2, 3.3, 3.6, 10; CLAUDE.md «Архитектурные правила» 1–3, 5, 7, 8; backlog F-031, F-066, F-075–F-077; решения заказчика В-01, В-05, В-07, В-12

## Контекст

- Команда маленькая, стадия MVP, релизы R1→R2→R3 (Q-03). Нагрузка пилота ничтожная: десятки участников, один ответ в день, дашборд на 50 × 365.
- ТЗ и CLAUDE.md уже фиксируют модульный монолит на Laravel и запрет на доступ к таблицам чужого модуля.
- Нужно, чтобы Telegram-бот, трекеры, алерты и биллинг добавлялись без переделки модулей Survey, Responses, Analytics (п. 3.3.3, раздел 10).
- Установка у клиента (on-premise) в R1 не входит (В-07), но принцип «вся конфигурация через env» сохраняется, чтобы её можно было добавить позже. Чем меньше развёртываемых единиц, тем проще это будет.

## Решение

**Одно Laravel-приложение (один деплой, одна БД), код разделён на модули** в `backend/app/Modules/<Module>/` (namespace `App\Modules\<Module>`), без сторонних пакетов модульности.

### Модули и владение данными

| Модуль | Отвечает за | Владеет таблицами (см. ADR-0004) |
| --- | --- | --- |
| Identity | Аккаунты, вход по коду, токены устройств, сессии, согласие ПДн, внешние идентичности, профиль, права субъекта ПДн (оркестрация) | `users`, `login_codes`, `personal_access_tokens`, `consent_documents`, `user_consents`, `external_identities` |
| Projects | Проекты, участие и роли, коды приглашения, заявки, флаги функций и тариф, рабочий календарь | `projects`, `memberships`, `invite_codes`, `join_requests`, `project_features` |
| Survey | Банк и вопросы проекта, версии, состав и ротация, «опрос дня», открытие и закрытие дня | `questions`, `question_versions`, `survey_configs`, `survey_config_items`, `survey_days`, `survey_day_questions` |
| Responses | Канал-независимый приём ответов, подписанные и анонимные комментарии, доступность анонимности | `responses`, `response_answers`, `anonymous_comments` |
| Analytics | Дневные агрегаты, индекс, участие, данные дашборда, экспорт CSV (PDF — R2) | `daily_member_stats`, `daily_project_stats`, `daily_question_stats`, `exports` |
| AI | R2. В R1 — пустой модуль с контрактом `LlmProvider` и событием `SummaryGenerated` | (R2) `ai_summaries`, `ai_summary_pseudonyms` |
| Notifications | Письма (коды, заявки), очередь `mail`, язык получателя | нет |
| Audit | Журнал действий, срок хранения 1 год | `audit_log` |
| Integrations | Пустой задел: контракт коннектора, таблица подключений | `integration_connections` |
| Shared (ядро) | Не модуль предметной области: `Channel`, `LocalDate`, единый формат ошибок, локализация API, базовые DTO | нет |

### Структура модуля

Следует правилу 8 CLAUDE.md: `Http/Controllers`, `Http/Requests`, `Contracts` (публичные интерфейсы модуля), `Services`, `Repositories` (+ интерфейсы), `DTO`, `Models`, `Events`, `Listeners`, `Jobs`, `Policies`, `Database/Migrations`, `Providers/<Module>ServiceProvider`, `routes`. Наружу модуль отдаёт только `Contracts`, `DTO`, `Events` и enum-ы. Модели Eloquent за пределы модуля не выходят.

### Как модули общаются

1. **Синхронно — через контракты.** Модуль A зависит от интерфейса `B\Contracts\XxxService` и получает DTO. Пример: Responses вызывает `Survey\Contracts\SurveyDayService::today(projectId)` и `Projects\Contracts\MembershipService::canAnswer(userId, projectId)`.
2. **Асинхронно — через доменные события Laravel** из п. 3.6: `MemberJoined`, `SurveyDayOpened`, `ResponseSubmitted`, `SurveyDayClosed`, `SummaryGenerated` (последнее объявляется в R1, публикуется в R2). Имена не меняются (правило 5). В событиях только идентификаторы и скаляры (`projectId`, `localDate`, `membershipId`): без моделей и без текста комментариев. Подписчики — queued listeners в своём модуле, очередь по назначению (`analytics`, `default`). Дополнительные события (например, `MemberRemoved`, `QuestionVersionCreated`, `AccountDeleted`, `ProjectDeleted`) добавляются по мере надобности; существующие не переименовываются.
3. **Реестры для сквозных операций с ПДн.** Каждый модуль, хранящий данные о пользователе или проекте, реализует контракт `PersonalDataLifecycle` с тремя операциями:
   - `export(userId)` — выгрузка «мои данные»;
   - `onAccountDeleted(userId)` / `onProjectDeleted(projectId)` — мягкое удаление, то есть скрытие данных (В-05, ADR-0005);
   - `purgeUser(userId)` / `purgeProject(projectId)` — физическое удаление, запускается вручную командой системного администратора.

   Identity и Projects вызывают все зарегистрированные реализации. В R2 модуль AI добавит свою реализацию (в том числе удаление записи словаря псевдонимов) без правок Identity.
4. **Внешние ключи между таблицами разных модулей допустимы** как гарантия целостности (`ON DELETE RESTRICT`), но каскадное удаление через границу модуля запрещено: удаление выполняется через реестр (п. 3). Запросы к чужим таблицам (JOIN, Eloquent-связи через границу) запрещены. Исключение — `user_consents.user_id` без внешнего ключа: запись должна пережить физическое удаление пользователя (В-11, ADR-0004).
5. **Контроль границ в CI.** `deptrac` (dev-зависимость, только CI) с правилом «модуль видит у соседа только `Contracts`, `DTO`, `Events`, enum-ы». Альтернатива без зависимости — architecture-тест на PHPUnit, сканирующий `use`. Выбор делаем при настройке CI.

### Каналы ответа (правила 2–3)

- Логика опроса находится в `Responses\Services\SurveyResponseService` и `Survey\Services\SurveyDayService`. Они получают `Channel` параметром и ничего не знают о HTTP.
- Канал определяет HTTP-слой (middleware в Shared) по способу аутентификации и типу клиента токена, а не по полю из тела запроса: сессия → `web`, токен устройства с клиентом `extension` → `extension`. Будущий Telegram-адаптер вызовет тот же сервис с `Channel::Telegram`; enum `Channel` уже содержит `telegram`.
- Ответ API опроса содержит полное описание вопросов (тип, варианты, ограничения, тексты ru/en), достаточное для отрисовки в любом клиенте.

### Кабинет и API (В-01 — решено)

- **Каналы ответа** (расширение, `/survey`, будущий бот и мобильные приложения) работают только через `/api/v1/...` (Sanctum: токен или сессия), описанный в OpenAPI.
- **Кабинет** (Inertia + Vue) — серверные маршруты Inertia с сессией, вызывающие те же сервисы модулей. REST API для кабинета не делаем (решение заказчика В-01). Страница профиля (устройства, выгрузка, удаление аккаунта) — тоже Inertia-страница, доступная любому аккаунту без роли в проекте (В-14).

### Точки расширения на следующие этапы

| Этап | Точка расширения |
| --- | --- |
| Telegram-бот | `Channel::Telegram`, `external_identities`, канал-независимые сервисы, самодостаточное описание вопросов в API |
| Трекеры | Модуль Integrations: `integration_connections` + контракт `TrackerConnector`; в Analytics контракт `MetricSource` (опрос — первый источник) |
| Алерты | Доменные события + флаг `alerts` в `project_features` (выключен) |
| Тарифы | `projects.plan = 'pilot'`, лимиты из `config/plans.php` через `Projects\Contracts\PlanLimits` |
| Мобильные приложения | Токены устройств с типом клиента `mobile` — без изменений модулей |
| Установка у клиента (после R1) | Вся конфигурация через env, один compose (ADR-0007); поле «адрес сервера» в расширении (ADR-0003) |

## Рассмотренные альтернативы

1. **Классический монолит Laravel без модулей.** Быстрее на старте, но правило «модуль не трогает чужие таблицы» нечем поддерживать, а ТЗ прямо требует модули. Отклонено.
2. **Микросервисы / отдельные сервисы (например, AI и Analytics).** Изоляция и независимое масштабирование при нагрузке пилота не нужны. При этом добавляются сеть, брокер, распределённые транзакции и несколько деплоев. Отклонено. Модульность оставляет возможность выделить AI-воркер позже.
3. **Пакет `nwidart/laravel-modules`.** Даёт генераторы и автозагрузку, но это лишняя зависимость со своими соглашениями; PSR-4 и по провайдеру на модуль достаточно. Отклонено.
4. **Кабинет тоже через `/api/v1` (SPA-подход).** Отклонено заказчиком (В-01).

## Последствия

- (+) Один деплой, одна БД, транзакции внутри процесса.
- (+) Новые каналы и функции R2 добавляются новыми адаптерами, слушателями и реализациями контрактов.
- (+) Мягкое и физическое удаление — одна точка расширения на модуль, физическое удаление покрывается теми же тестами.
- (−) Границы держатся на дисциплине и проверке в CI; без неё модули быстро срастутся.
- (−) Чтение «через сервис» иногда дороже JOIN-а; для дашборда это снимается агрегатами Analytics (ADR-0004).
- (−) Мобильному приложению кабинета (если появится) понадобится отдельный REST — сервисы к этому готовы.
- Каждый новый тип сущности (ServiceProvider модуля, Event, Listener, Job, Policy, Contract, Enum, Value Object, реализация `PersonalDataLifecycle`) описывается в `docs/new_types.md` при первой реализации (правило 8 CLAUDE.md, решение В-12).
