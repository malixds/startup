# Пульс команды — инструкции для Claude

Пилот системы пульс-опросов для IT-команд. Сотрудники по рабочим дням проходят короткий опрос (расширение браузера или веб-страница), руководитель видит динамику и запрашивает AI-сводку.

Полное ТЗ: `.claude/TZ/TZ_Puls_komandy.md` (главный документ; PDF рядом — справочный). Бэклог, релизы и решения заказчика: `docs/product/backlog.md`. Перед задачей по конкретной фиче читай соответствующий раздел ТЗ. Если код и ТЗ расходятся или ТЗ противоречиво либо неполно — действуй по разделу «Когда спрашивать меня».

> Стартовая версия файла составлена по ТЗ до появления кода. Пункты с пометкой «уточнить» заменить реальными значениями после первых коммитов.

## Когда спрашивать меня

Спрашивай ТОЛЬКО если вопрос касается:
- архитектуры и выбора технологий;
- персональных данных, безопасности и юридических рисков;
- денег, сроков и объёма релиза;
- прямого противоречия в ТЗ, которое меняет поведение для пользователя.

Всё остальное (пограничные случаи, детали формул, порядок событий, мелкие правила) решай сам: выбирай самый простой и последовательный вариант, записывай решение в `docs/decisions.md` одной строкой и иди дальше. Я просмотрю этот файл, когда захочу.

## Стек

- Backend: PHP + Laravel (актуальные стабильные версии), модульный монолит
- БД: PostgreSQL 16+
- Очереди и кеш: Redis + Laravel Queue + Horizon, периодические задачи — Laravel Scheduler
- Auth: Laravel Sanctum (токены устройств для расширения, сессии для веб-приложения), вход только по коду из письма, паролей нет
- Frontend веб-приложения: Inertia + Vue
- Расширение: TypeScript, WebExtensions API, Manifest V3, один код для Chrome, Яндекс Браузера, Edge, Firefox, Safari (WXT или аналог)
- Окружение: Docker Compose, Nginx + PHP-FPM

## Структура репозитория (предлагаемая, уточнить)

- `backend/` — Laravel
- `backend/app/Modules/<Module>/` — модули: Identity, Projects, Survey, Responses, Analytics, AI, Notifications, Audit, Integrations (пустой задел)
- `extension/` — браузерное расширение
- `docs/` — OpenAPI-спецификация, ER-диаграмма, продуктовые документы (`docs/product/`). ТЗ в `docs/` не переносится

## Команды (уточнить после настройки окружения)

- Запуск: `docker compose up -d`
- Тесты: `docker compose exec app php artisan test`
- Стиль PHP: `docker compose exec app ./vendor/bin/pint`
- Статический анализ: `docker compose exec app ./vendor/bin/phpstan analyse` (Larastan, уровень не ниже 6)
- Расширение: `npm --prefix extension run lint` и `npm --prefix extension run build`

Перед тем как считать задачу готовой: тесты, Pint и PHPStan проходят без ошибок. CI блокирует слияние при красном статусе.

## Архитектурные правила

1. Модуль не обращается к таблицам другого модуля напрямую. Только через сервисы модуля или доменные события.
2. Все каналы ответа (расширение, `/survey`, будущий Telegram-бот) используют одни и те же эндпоинты `/api/v1/...`. Логика опроса живёт в сервисе, не зависящем от канала. Каждый ответ хранит поле `channel`.
3. Новый канал ответа не должен требовать изменений в модулях Survey, Responses, Analytics.
4. Права проверяются только на backend через Policies или Gates, на каждый запрос. Скрытие кнопки в интерфейсе защитой не считается.
5. Доменные события: `MemberJoined`, `SurveyDayOpened`, `ResponseSubmitted`, `SurveyDayClosed`, `SummaryGenerated`, `MemberParticipationChanged`. Не переименовывать без согласования: на них строятся будущие алерты.
6. Лимиты и тарифные ограничения читать из конфигурации и флагов функций проекта, не зашивать в код.
7. Вся конфигурация через переменные окружения, чтобы в будущем систему можно было развернуть on-premise. Поставка on-premise в релиз 1 не входит.
8. В основном работаем по: кастомный запрос, контроллер, интерфейс, репозитории, дто, модель, сервисы. Можно создавать и другие сущности, они требуется, но каждый новый тип сущности, например, провайдер регламентируй в файле `docs/new_types.md`, где после введение – будешь описывать: что это за сущность, в чем ее необходимость/удобность/полезность и как использовать.

## Роли

В проекте три роли: владелец (ровно один), администратор, сотрудник. Администратор может всё, что владелец, кроме назначения ролей, передачи владения и удаления проекта. Сотрудник только проходит опрос. Матрица прав — ТЗ, п. 2.2. Любой новый эндпоинт покрывается feature-тестом на эту матрицу.

## Опрос и время

- Опрос по рабочим дням пн–пт. Дни недели хранятся настройкой проекта.
- Метки времени в UTC. «День опроса» — локальная дата в часовом поясе **проекта**, отдельное поле типа `date`.
- Набор вопросов дня фиксируется при открытии дня. Изменения настроек действуют со следующего рабочего дня.
- Один ответ на участника в день, до закрытия дня его можно изменить.
- Изменение вопроса, на который уже отвечали, создаёт новую версию. Ответ ссылается на версию.
- Индекс команды 0–100, формула в ТЗ, п. 7.3. Покрыт unit-тестами.

## Персональные данные и безопасность

- Токены устройств и коды входа хранятся только хэшами.
- Код приглашения хранится как HMAC (для поиска) и зашифрованная копия (для показа владельцу и администратору по п. 2.2 ТЗ). Ключи HMAC и шифрования только в `.env`. См. ADR-0004.
- Анонимных ответов и комментариев нет: все ответы и комментарии привязаны к участнику (решение заказчика 2026-10-27, отступление от ТЗ, см. ADR-0005).
- При удалении аккаунта, проекта или исключении участника с удалением ответов данные удаляются физически и сразу. Мягкого удаления (`deleted_at`) нет.
- С ответами не хранить IP-адреса.
- Согласие на обработку ПДн — отдельный экран и отдельная запись с версией текста.
- В интерфейсе и промптах не использовать медицинские термины и диагнозы («выгорание», «депрессия»). Используем «энергия», «нагрузка», «самочувствие».
- Администратор одного проекта никогда не видит данные другого. Тест на каждый эндпоинт.
- Секреты и ключи API только в `.env`, никогда в коде и коммитах.

## AI-сводка

- Провайдеры только через интерфейс `LlmProvider`. Новый провайдер — новый класс и запись в `config/ai.php`, без правок остального кода. Для тестов — `FakeProvider`.
- В провайдера уходят только псевдонимы («Участник 1»). Имена, email, название проекта и компании не отправляются. Словарь псевдонимов не покидает систему.
- Ответ модели — строгий JSON по схеме из ТЗ, п. 8.3, с валидацией. Запросы идут через очередь `ai`.
- Промпты — версионированные файлы в `resources/prompts/`, не строки в коде.

## Очереди

- Очереди по назначению: `mail`, `ai`, `analytics`, `default`. Письма с кодами входа не должны ждать за запросами к нейросети.
- Задачи идемпотентны, с повторными попытками и логированием окончательного сбоя.

## Расширение

- Разрешения только `storage`, `alarms` и домен API. Не запрашивать доступ к вкладкам, истории, содержимому страниц.
- Бейдж — число проектов с непройденным опросом. Системных уведомлений в пилоте нет.
- После отправки — экран «Молодец!» (en: «Well done!»).

## Локализация

Все строки интерфейса, писем и ошибок — в языковых файлах ru и en. Текст в коде не хардкодить.

## Как работать

- Миграции обратимы. Не редактировать уже применённые миграции, создавать новые.
- При изменении API обновлять спецификацию OpenAPI в `docs/` в том же коммите.
- Новые зависимости добавлять только с объяснением, зачем они нужны.
- Не реализовывать вне задачи то, что ТЗ относит к следующим этапам (раздел 10): Telegram-бот, трекеры, алерты, оплата. Закладывать только точки расширения.
